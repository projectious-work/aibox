# 18. Executable operational contracts and quality limits

This chapter completes R-RESULT, R-EXECUTION, R-POLICY, R-RECOVERY and
R-CONFIG. The schemas generated by `scripts/contracts.mjs` and the rules here
are normative. Requirements elsewhere must agree with them; a conflict is a
specification defect, never permission to select whichever text is convenient.

## Request and result specialization

`operation-request.schema.json` is a closed union with a separate property
set for every operation. A field valid for one operation is not automatically
valid for another. The wire names in that schema are the core operation names.
CLI adapters resolve relative selectors and supply defaults before constructing
the normalized request. MCP adapters require canonical absolute paths. Neither
adapter accepts a caller-provided actor, executable path, policy or environment
blob. Request IDs are 1–128 ASCII identifier characters; the CLI generates a
UUID when omitted. No semantics are attached to a UUID beyond correlation.

| Operation family | Required selector / defaults | Result `data` |
|---|---|---|
| Build/start | Root, runtime context, expected input digest; frozen lockfile defaults true | Built image identities, or observed resources and retained-data references |
| Stop/remove/rebuild | Above plus exact primary resource ID; remove/rebuild require `acknowledgeDisruption=true` | Observed primary/owned sidecar states and retained-data references |
| Inspect environment/workspace | Root; operator inspection requires runtime context; expected digest optional | State, resource list, timestamp, redacted configuration/provenance entries |
| Check environment/workspace | Root; offline true, empty check list means all eligible checks | Findings and `complete`; requested unavailable/denied checks cannot be reported healthy |
| Read logs | Root, declared source, 1–1000 lines, optional RFC 3339 `since` | Bounded entries and explicit truncation; runtime source is operator-only |
| Refresh workspace | Root, expected UX input digest, scope `all`, `theme` or `tmux` | Changed files, rebuild and session-restart flags; optional theme/mode/layout overrides are invocation-only |
| Inspect operation | Root and operation ID | Durable state, original operation, last confirmed step, known/unknown effects and closed next action |
| Migration preview/apply/rollback | CLI and MCP; preview source/destination roots; apply/rollback plan ID and digest under explicit operator authorization | Plan/manifest reference, conflicts and whether activation occurred |

`data` is required for successful/no-change/rebuild-required results and has an
operation-specific closed schema. Diagnostics belong in findings, not free-text
warnings masquerading as a machine payload. Configuration entries identify the
domain, winning layer/source and redaction status. Native structured values
remain JSON values, within the limits below; do not serialize an entire secret-
bearing environment into a string. Findings sort by code then source/path;
resources sort by kind then native ID. Lists with user-defined order retain it.
Successful build must report at least one inspected image identity; successful
start/rebuild must report a running primary, or fail the postcondition. These
semantic checks supplement schema shape. Do not return empty success payloads
merely because a delegated process exited zero.

An initial build, absent environment, denied request or parser failure may have
no native resource ID. `target` and `inputDigest` are absent if unresolved,
never fabricated. Successful reads/builds do not require a container ID.
Bootstrap failures use operation `invalid_request` and a generated request ID
when the request could not be parsed. `--format json|yaml` still emits one
valid error envelope when the format can be safely determined; otherwise
bootstrap errors use stderr and exit 2. Help, version and shell completion have
their own documented text/metadata output; interactive `attach` rejects JSON
or YAML because its stdout is the terminal session.

Outcomes are `succeeded`, `no_change`, `rebuild_required`, `failed`, `refused`,
`timed_out`, `cancelled`, and `partial`. Error-bearing outcomes require a
structured error with `retryable` and a closed `nextAction` enum. Partial
results also carry `completedEffects` and `unknownEffects`; empty completed
effects does not imply no effects if inspection failed. The optional message
explains a closed next action; it never becomes executable recovery text.

| Stable error code / category | CLI exit | Retry behavior |
|---|---|---|
| `invalid_input`, `unknown_version`, `input_changed` / invalid_input | 2 | Correct/reinspect; never automatically retry mutation |
| `not_authorized`, `approval_expired`, `identity_changed` / denied | 3 | External authorization or fresh inspection required |
| `dependency_missing`, `dependency_incompatible` / missing_dependency or incompatible | 4 | Advisory installation/update; no auto-install |
| `busy`, `child_failed`, `postcondition_failed`, `operation_record_unavailable`, `internal_error` | 5 | `busy` allows a later read; mutation failures require inspection |
| `rebuild_required`, `session_restart_required`, `migration_conflict`, `recovery_required` | 6 | Explicit operator/user action |
| `operation_timeout` / timeout | 124 | Timeout without observed effects is `timed_out`; with effects/uncertainty is `partial` |
| `operation_cancelled` / interrupted | 130 | Cancellation without effects is `cancelled`; with effects/uncertainty is `partial`, still exit 130 |

Doctor: complete run with no failed error/warning is exit 0; failed warnings or
incomplete explicitly requested checks require action (6); failed errors use
the applicable 2/3/4/5 class, with precedence 3, 2, 4, 5, 6. Informational
findings do not fail the command. MCP returns domain failures as tool results
with `isError=true` and the same structured envelope; malformed protocol input
uses SDK protocol errors. It does not turn a denied tool call into protocol
success merely because JSON was returned.

## Principal, capability and operation approval

`aibox mcp serve --context knowledge|local|operator` selects the registry;
default is knowledge. Operator context requires `--policy ABSOLUTE_PATH`.
Local context has no runtime client. CLI defaults to operator context for
lifecycle commands and local context for refresh; read commands accept an
explicit context. An entry-context flag is not a sandbox or an authority grant.

`operator-policy.schema.json` defines the concrete host-owned file. It binds
an OS principal/service identity, permitted roots, executable invocation paths,
named runtime endpoint fingerprints, operation capabilities and expiring
digest-bound grants. The server validates ownership and rejects a policy
inside a writable project or writable by the container user. The policy is
loaded once; changes need an explicit process restart. Human CLI confirmation
may create an in-memory grant for that single invocation under the configured
policy and must be recorded in its operation record. `--yes` supplies acknowledgement,
not independent authority. MCP never asks itself to approve a mutation.

An MCP grant matches requester (the externally configured stdio connection
principal), canonical root/config, operation, runtime context, input digest,
expiry, and existing resource ID where relevant. Missing match means refusal.
There is no `approve` MCP tool and no repository-controlled grant. A host human
edits the policy using ordinary file tools. OS administration and the trusted
operator can naturally bypass application policy through native runtime tools;
this design does not claim isolation against the same OS principal that owns
the policy. Use distinct service accounts/permissions where separation from
the calling agent is required. Client name, MCP initialization metadata and
Git author are attribution only, never authenticated identity.

Before effects: parse → validate → establish principal → resolve selectors →
authorize capability/grant → acquire lock → revalidate identities/digests →
persist operation record → execute. Pure discovery needed to compute the digest uses
only separately permitted read operations. Required-sink and operation record checks
run before execution. A request cannot disable them through higher-precedence
settings. Local calls never acquire an operator client or policy path.

The fixed registry exposes the declared lifecycle tools and
`inspect_operation`; local mode exposes `inspect_workspace`, `check_workspace`,
`refresh_workspace`, `read_logs` for local sources, and `inspect_operation`
for local operation records. V1-20 adds named migration preview/apply/rollback
tools with the same reviewable plan, digest and rollback semantics as the CLI;
apply/rollback require operator grants and never expose generic config editing.
Names, descriptions, schemas and
capability membership are release assets checked for collisions at startup.
Each MCP tool exposes its selected request-union branch as an object schema,
not the whole operation union. Local `read_logs` additionally excludes runtime
selectors and the runtime source enum; local operation record inspection cannot address
the host store. Server semantic authorization remains mandatory even where a
client ignores the advertised narrowed schema.

## Input binding and upstream delegation

The input manifest records root/config identity, byte hashes of selected
Dev Container/Dockerfile/Compose files, Feature lock, referenced local Feature
code, lifecycle scripts with statically identified paths, distribution assets,
policy digest, executable identity and relevant non-secret environment inputs.
Hash canonical JSON (sorted object keys, domain-order arrays preserved) with
SHA-256. Store the manifest without secrets. Secret files are references only;
credential rotation does not put low-entropy secret hashes into an operation record.
Sensitive environment values must not be included in public digest material.

The digest detects changes in the declared control-input set; it is **not**
a claim that arbitrary build context or shell dependencies are immutable.
Host hooks are denied by default. Granting them requires an operator-controlled
read-only snapshot of all host-executed code and reviewed mount paths; a hook
that loads code from a workspace writable by the container agent is refused.
Ordinary builds run project code in the native build environment. No approval
can add a host runtime socket or operator credentials to the workspace.
Revalidate paths after lock acquisition and before each native mutation;
unexpected changes yield `input_changed` before the next side effect.

The public upstream selector is `--config <absolute devcontainer.json>` with
`--workspace-folder <canonical root>`. Build/up pass `--frozen-lockfile` when
requested (default true); a missing lock blocks frozen operation. A new user
may explicitly select non-frozen build to let the upstream CLI create its
native lockfile, then review/freeze it. aibox never fabricates a second lock.
Read configuration uses `read-configuration`; merged metadata that needs
registry access is unavailable in offline doctor, not silently fetched.
Build/rebuild expose `noCache` (`--no-cache`, default false); delegate to
`devcontainer build --no-cache`. Rebuild must also pass `up --build-no-cache`
when it may build again. These spellings are verified against the
[pinned CLI source](https://github.com/devcontainers/cli/blob/5dc7533314b5ba7ec3875c30143dfe1aec644870/src/spec-node/devContainersSpecCLI.ts).
Retest against the qualified release; do not claim cache bypass merely
because the preflight bypassed cache.
Resolve `--docker-path`/Compose executable through policy. Pin/probe the exact
CLI command surface during V1-03; no private Node imports are allowed.

Rebuild performs a non-destructive build preflight before stopping/removing
the exact old primary and owned sidecars, then delegates normal `up`. Native
`up` may rebuild; the preflight image is not guaranteed to be reused and is
not advertised as an atomic image swap. Failure before removal leaves the
old environment intact; failure afterward is partial and requires recovery
from retained data and the pinned previous definition. Record actual final
image identities. Do not invent an override file to force image reuse.

## Environment membership and durable recovery

An environment is its primary Dev Container and its selected **exclusively
owned** Compose sidecars. Resolve services using the native Compose model and
inspect their exact IDs, project/config labels and endpoint. Shared services
are reported but never stopped/removed by this operation. Record membership
before mutation, and revalidate every ID. Stop owned services in reverse
dependency order, start via upstream `up`, and remove exact container IDs
without deleting volumes, images, unrelated services or networks. Runtime
networks left by native tools are listed as retained resources with native
cleanup guidance; no broad `compose down`/prune is implied. An ambiguous
membership or a replica change blocks mutation rather than widening scope.

Operation record storage is `${XDG_STATE_HOME:-$HOME/.local/state}/aibox/operations/`;
host and container stores are physically distinct. Directories are 0700,
files 0600. `operation-record.schema.json` fixes the record. Write a temporary
file on the same filesystem, fsync, rename, then fsync the directory. Update
after each observed step. The lock is an OS advisory lock on a SHA-256 key of
canonical root + config path + endpoint identity; keep its file rather than
unlinking a lock another process might hold. Do not rely on a PID file alone.

`aibox operation status <id> --project <root>` and `inspect_operation` read
the operation record after the same root/actor checks. Terminal results can be returned
for the same request ID only when normalized request fingerprint and target
still match; mismatch is `invalid_input`. Interrupted/executing operation records are
inspection-only on replay. A fresh mutating request must first reconcile
native state; the wrapper never blindly resumes destructive steps. This gives
another client a recovery path without conversation history or a daemon.

Keep incomplete/partial operation records until explicitly resolved by the operator.
Retain terminal operation records 30 days and ID/fingerprint tombstones 180 days;
expired tombstones do not promise perpetual replay detection. Clients use new
UUIDs for new intent. Cleanup of operation records is a bounded local maintenance task,
never a side effect of log rotation or container removal. Evidence exports
use relative file locators plus hashes; public records cannot rely solely on
producer-local absolute paths.

## Measurable limits and failure tests

**R-LIMITS:** enforce these default limits before allocating or delegating.
They are product defaults, not permission for repository overrides.

| Surface | Limit / test |
|---|---|
| CLI/MCP application input/result | 1 MiB encoded each; paths 4096 characters; identifiers 128; reject excess with invalid_input |
| Parallel requests | One mutation per environment lock; at most 4 concurrent inspections per server, queue 32, excess returns busy |
| Child diagnostics | 256 KiB redacted rolling tail per stream; mark truncation; never let a noisy child consume unbounded memory |
| Cancellation | TERM process group, wait 5 seconds, then KILL where supported; inspect for up to 10 seconds; unknown effects mean partial |
| Timeout | 3600 seconds mutating command, 30 seconds inspect/check unless an explicit bounded setting changes it; runtime unavailability must not hang doctor |
| Guides | Index <=16 KiB; topic <=64 KiB; embedded and usable offline; no repository crawl |
| Sidebar | Poll at most once/second while visible, stop hidden polling; stale after 10 seconds by default; separate provider rate limits/cache TTLs still apply |
| Preview | 5 seconds/render, 20 MiB input by default, 1 MiB captured text; oversized files get bounded text/metadata fallback; LaTeX compilation is a separate explicit job |
| Local overhead | On a recorded 2-core/4-GiB Linux test VM, 30 warm runs: p95 help/version/guide <=500 ms, wrapper overhead <=500 ms excluding delegated tool execution |

Known secrets are redacted across chunk boundaries before output reaches a
sink. No claim is made to recognize every unknown secret. Untrusted child
output is excluded from durable evidence by default; diagnostics use bounded
sanitized excerpts. Retention of provider auth in home is intentional and
separate from the no-secret diagnostic contract in chapter 17.

**AC-CONTRACTS:** validate every schema with a Draft 2020-12 implementation
including format checks; cover each operation's successful payload, refusal,
missing resource, timeout, partial effects, wrong-context and irrelevant-field
rejection. Test a fresh client inspecting an interrupted request, stale
grants, Compose primary/sidecar/shared membership and the limits above.
Generated SDK schemas must accept/reject the same fixtures. These schema
fixtures prove contract coherence, not runtime or security implementation.
